# Устройства, которые запустили приложение, но не отправили запрос в Trisigma

Выборка по логам Ingress (`mpback-k8s-ingress-*`): устройства с версией приложения **строго выше 11.10.0**, у которых после запуска нет ни одного запроса в Trisigma Composition. Те, у кого запрос всё-таки нашёлся (позже или только в `mpback-k8s-trisigma-composition-*`), убираются из выборки и попадают в отдельный файл с указанием, где и когда запрос найден.

| | что это | когда брать |
|---|---|---|
| `find_no_trisigma.py` | скрипт (Python 3.8+, только стандартная библиотека): запрос + проверка кандидатов + CSV | основной способ |
| `devtools.txt` | те же шаги блоками для Kibana Dev Tools | быстро посмотреть, ничего не ставя |

Названия полей по умолчанию сняты с реальных документов: `log.http_user_agent` (JSON, внутри `"id"` = id устройства = `visitorId`), `log.request_url`, `log.status`, `log.http_x_burgerking_version` / `_platform` / `_user_id`, `log.request_hostname` (фильтр `orderapp.burgerkingrus.ru`).

## Как запустить скрипт (Kibana + логин и пароль)

1. Нужен Python 3.8+ (`python3 --version`), больше ничего ставить не надо. Скачайте `find_no_trisigma.py`.
2. Задайте адрес Kibana и учётные данные (переменные окружения; пароль не попадёт в историю команд, если задать его так):

   ```bash
   export KIBANA_URL=https://<адрес-kibana>
   export ES_USER=<логин>
   export ES_PASSWORD=<пароль>
   ```
   Windows PowerShell: `$env:KIBANA_URL="https://..."; $env:ES_USER="..."; $env:ES_PASSWORD="..."`.
3. Проверка подключения и полей:

   ```bash
   python3 find_no_trisigma.py discover
   ```
   Выведет версию Elasticsearch, поля и по документу из каждого индекса. Если так и есть (`log.http_user_agent`, `log.request_url` и т.д.), идите дальше.
4. Проверка фильтров на коротком окне (в конце должно быть `OK`):

   ```bash
   python3 find_no_trisigma.py sanity --from 2026-09-28T00:00:00Z --to 2026-09-28T03:00:00Z
   ```
5. Сама выборка (окна `--from/--to` в UTC, МСК = UTC+3; суточное окно при таком фильтре по версии лёгкое):

   ```bash
   python3 find_no_trisigma.py run --from 2026-09-28T00:00:00Z --to 2026-09-29T00:00:00Z --out result
   ```
6. Перепроверка старой выгрузки: у кого из неё на самом деле был запрос, где и через сколько минут:

   ```bash
   python3 find_no_trisigma.py audit старая_выгрузка.csv --out old
   ```

Проблемы с подключением:
- `certificate verify failed` (корпоративный сертификат): `--cacert файл.pem` или, если это внутренний Kibana, `--insecure`.
- 401 / страница входа: Kibana за SSO. Тогда логин и пароль не подойдут; войдите в браузере, скопируйте cookie из запроса в DevTools и передайте `-H "Cookie: sid=..."` (или используйте API-ключ: `ES_API_KEY`).
- Прямой доступ к Elasticsearch вместо Kibana: `ES_URL=https://...:9200` вместо `KIBANA_URL`.
- Скрипт пишет `Unknown column [...]` / `в индексе нет поля`: покажите вывод `discover`, поправим имя (`--set device=...` и т.п.).

## Что считается запуском, запросом и «ошибкой»

- **Единица — устройство.** `visitorId` в Trisigma = id из `user-agent` = `device_uuid`; `userId` необязателен и неавторизованным не уходит. `user_id` в выгрузке только для справки.
- **Запуск** = устройство (ios/android) обратилось не менее чем в 6 разных сервисов шлюза (`/gateway/<сервис>/…`) за одну минуту, веер запросов при старте (на реальных логах 6–10, ключ `fanout_min`). Колонка `gap_before_min` — сколько устройство молчало перед запуском; `--set min_gap_min=60` оставит только «холодные» старты.
- **Запрос в trisigma** = любой запрос, в пути которого есть `trisigma` (`features` при запуске, авторизации и выходе; `experiments`). **С любым HTTP-статусом:** 401 значит, что приложение запрос отправило, а бэкенд его отклонил, так что в Composition он не попадает. Чтобы 401/5xx запросом не считались: `--set tri_ok_only=true` (в выборку попадут и такие устройства).
- **Нет запроса после запуска.** Шаг 1 (ES|QL): ни одного запроса с (минута первого запуска − 2 мин) до конца окна + 30 мин. Шаг 2 (проверка кандидатов): то же **без верхней границы по времени**, в Ingress и в индексе composition (id устройства ищется в User-Agent входящего запроса и в теле запроса к Trisigma). Нашёлся — устройство исключено.
- **Версия.** `11.11.0_384`, `11.11.0-rc-08.g_20269`, `11.10.1.g_20300` → числовая тройка, порог **строгий** (> 11.10.0). «11.10.0 и выше»: `--set inclusive=true`. В старой выгрузке 32 строки на 11.9.0 и 13 ровно на 11.10.0, выше ни одной.
- Строки trisigma учитываются даже без версии/платформы; версия и платформа проверяются только для стороны «запуск».

### Почему в старой выгрузке могли быть «ошибочные» (гипотезы)
1. запрос пришёл позже окна проверки; 2. сопоставление по `user_id` (`features` уходит при запуске, авторизации и выходе, и `http_x_burgerking_user_id` в логе может быть пустым); 3. запрос виден только в composition или путь чуть другой; 4. упавшие запросы посчитаны как «запроса нет». `audit` показывает, какая из них верна.

## Файлы результата (`;`-разделитель, как в старой выгрузке)

- `result_final.csv`: `user_id, device_id, platform, app_version, first_launch_utc, gap_before_min, launch_bursts, max_fanout_services, last_seen_utc`;
- `result_excluded.csv`: исключённые: причина, где (`ingress` / `composition`), когда и по какому пути найден запрос;
- `result_level1_all.csv`: кандидаты до проверки; `result_intersection.csv`: только при `events_index`.

`first_launch_utc` — начало минуты веера.

## Настройки (`--set имя=значение` или словарь `CFG` в начале файла)

| ключ | по умолчанию | что это |
|---|---|---|
| `ingress_index`, `comp_index` | `mpback-k8s-ingress-*`, `mpback-k8s-trisigma-composition-*` | индексы |
| `host`, `host_value` | `log.request_hostname`, `orderapp.burgerkingrus.ru` | фильтр хоста API приложения (пустое `host_value` = без фильтра) |
| `device`, `device_grok` | `log.http_user_agent`, `\"id\"%{SPACE}:%{SPACE}\"%{DATA:dev}\"` | откуда и как достать id устройства |
| `user`, `platform`, `version`, `path`, `status` | `log.http_x_burgerking_user_id` и т.д. | остальные поля Ingress |
| `comp_device` | User-Agent входящего запроса и тело запроса к Trisigma | где в composition искать id (через запятую) |
| `fanout_min`, `min_gap_min` | `6`, `0` | что считать запуском |
| `min_version`, `inclusive` | `11.10.0`, `false` | порог версии |
| `tri_ok_only` | `false` | `true`: запросом считается только статус < 400 |
| `buffer_min`, `pre_margin_min` | `30`, `2` | минуты после окна и до запуска для запросов в trisigma |
| `events_index`, `ev_key`, `ev_key_source`, `ev_experiment` | пусто, `device_id`, `device`, `experiment` | пересечение с событиями (ниже) |

### Пересечение с событиями без эксперимента
`--set events_index='<индекс событий>*' --set ev_key=<поле устройства или пользователя> --set ev_experiment=<поле эксперимента>` (для `user_id`: `--set ev_key_source=user`). В пересечение попадает устройство, у которого в окне есть события и ни в одном нет эксперимента (поля нет, `null`, `""`, `[]`). Колонки `events_total`, `events_with_experiment`, `intersection` (`yes` / `no` / `unknown`).

## Ограничения и что проверено

- Проверено на локальном Elasticsearch 8.14.3, 8.19.22 и 9.1.10: синтетические логи в вашей схеме (`tests/run_local.sh`) и 4827 реальных документов Ingress из вашей выгрузки за 28.09 (скрипт нашёл двух известных кандидатов). К вашему Kibana доступа не было, режим `--kibana-url` проверен на эмуляторе прокси Dev Tools.
- ES|QL нужен 8.14+ (`GET /` покажет версию). На старом кластере шаг 1 не заработает (скрипт скажет), `audit` и шаг 2 на обычном DSL, но на 7.x не проверялось.
- Запуск считается по минутным корзинам: веер, разорванный границей минуты, не засчитается.
- Индекс composition содержит только запросы, дошедшие до сервиса (401 на шлюзе туда не попадают).
